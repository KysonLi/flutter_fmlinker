# ISLI 盾牌码解码器优化总结报告

> 范围：`src/main/cpp/isli/` 全部源码 + 多轮真机测试图（101/207/110 张）
> 方法：PC 测试程序 + A/B 双模式对比 + 失败阶段埋点
> 周期：2026-07 ~ 2026-08

---

## 一、概述

### 1.1 起始问题

App 运行后输出大量日志、卡死崩溃。怀疑解码算法存在严重错误。

### 1.2 核心结论

| 项 | 状态 |
|----|------|
| 卡死崩溃根因 | ✅ 斜线生成器死循环（**非**追踪算法本身） |
| 解码率 | ✅ 7 → 31（**~4.4×**），优于 Android 参考实现 |
| HIT 零回归 | ✅ 构造保证（try-both 先跑 mode 0） |
| 误报 | ✅ 无（BCH re-encode 校验） |

---

## 二、优化方法论

为避免"凭感觉改算法"，建立了一套可量化的验证基础设施：

### 2.1 PC 测试程序（`test_data/test_isli_icon.cpp`）

- 用 `stb_image.h` 加载 PGM/PNG，在 PC（MSVC Release）上跑完整解码流水线
- 批量跑目录，从文件名提取期望结果（`HIT`/`MISS`）和参考耗时
- 支持 A/B 双模式：每张图跑两种配置，输出对比表 + 汇总（净增益、仅一方成功、回归数）
- PC 比 Android 快 50-100×（<1ms/帧 vs 10-144ms），迭代极快

### 2.2 失败阶段埋点（`islii_get_last_fail_stage()`）

在解码流水线每个失败点记录阶段：
```
0=成功  1=locate(未检测到盾牌)  2=trace(追踪脱轨)  3=curve  4=wave  5=bch
```
用于定位瓶颈到底在哪一阶段，而非笼统的"解码失败"。

### 2.3 追踪进度埋点（`islii_get_last_trace_progress()`）

记录追踪脱轨前走过的点数，判断"边框是基本完整（在角点脱轨，可救）"还是"开头就断（不可救）"。

### 2.4 决策原则

**任何改动必须 A/B 验证：净解码数提升且 HIT 零回归才合并。** 被证伪的方案保留代码但默认关闭。

## 三、根因修复：斜线生成器死循环（P0）

### 3.1 现象

App 卡死崩溃。PC 测试程序在 `isliicon.png` 上 hang 住（>3 分钟无输出）。

### 3.2 根因

`ISLIIconLocator.cpp` 的斜线扫描延迟生成器 `next_skew_line`：首条对角线的返回条件 `st->i == 1 && st->end0 == 0 && st->end1 == 0` 在每次调用都成立，导致**重复返回同一条线 → 死循环**。

### 3.3 修复

引入 `diag_done` 标记确保首条对角线仅返回一次，`phase` 状态交替输出上/下半区斜线。

### 3.4 验证

修复后 PC 解码器在 7 张 HIT 上全部成功，耗时 <1ms。**这是用户报告问题的真正根因。**

## 四、已落地的微优化（性能向）

这些是纯性能优化，不影响解码正确性，主要解决实时预览下的延时问题：

| 优化 | 文件 | 效果 |
|------|------|------|
| **内存池预分配** | 新增 `DecoderMemoryPool.h` | 消除每帧 ~15 次 new/delete，init 时一次性分配 |
| **calc_center_shift 单次遍历** | `FrameTracer.cpp` | 十字线子采样估阈值 + 单次遍历算质心，消除原双次遍历 |
| **二值化快速路径** | `Binarization.cpp` / `ISLIIconLocator.cpp` | 先全局阈值匹配，90%+ 场景跳过自适应阈值精化 |
| **高斯核缓存** | `CornerFinetuner.cpp` | 按半径缓存，4 角点共享同一核，避免重复 `exp()` |
| **CurveFit 幂次预计算** | `CurveFit.cpp` | 预算 x⁰..x⁶，替换 calcA/calcB 内重循环，提速 ~80% |
| **斜线延迟生成** | `ISLIIconLocator.cpp` | 迭代器逐条生成，替代预分配全部 ~300 条斜线 |
| **atan2 替换 deriv2angle** | `CornerFinder.cpp` | 8 分支手动象限判断 → 单次 atan2，~50 行→4 行 |
| **BS 计数门控跳过完整二值化** | `ISLIIconLocator.cpp` | 快速二值化 BS 数 < 8 时跳过完整回退，空帧扫描线免跑昂贵自适应阈值 |
| **快速模式开关 (`fast_mode`)** | 多处 | 综合性能选项：加倍定位步长+减半追踪迭代+跳过112-bit+跳过mode-2重试。A/B 实测：19→10 解码（含4 HIT 回归），预估 ~2-3× 加速。`islii_set_fast_mode(1)` 启用。 |

## 五、已落地的正确性优化（A/B 验证）

### 5.1 部分弧接受（+5 解码）

**问题**：追踪必须严格闭合（回到起点 ±step）才算成功；很多图走了 100+ 点但在角点脱轨，被整体丢弃。

**机制**（`FrameTracer.cpp::trace_once`）：脱轨但已走过 ≥100 点（盾牌周长约 167 点）的部分弧也接受，交由 corner_finder 处理近乎闭合的弧。

**A/B 结果**：15 → 20 解码（+5），7/7 HIT 零回归，全部输出正确码。

### 5.2 Stage-3 角点跳跃（+9 解码，核心突破）

**问题**：64 张图定位到盾牌但追踪脱轨，其中 33 张走了 ≥100 点（边框基本完整，在角点脱轨）。角点处两条相交边的暗像素把质心拉偏，导致 amend_center 无法收敛 → 脱轨。这是质心法的原理性缺陷，调参无法根治。

**机制**（`FrameTracer.cpp::trace_once`，`allow_jump`，mode 2）：追踪在角点脱轨（amend 返回 0）时，沿当前切向跨 `2.5×step` 跳过角点，在下一条边续追，最多跳 6 次。

**单 mode 2 的问题**：净 +6，但回归 2 张 HIT（HIT00009/33）—— mode 0 本可经由部分弧救回的图，被 mode 2 的跳跃弧替换后反而解不出。**不可接受。**

### 5.3 Try-Both 策略（最终方案，零回归）

**机制**（`ISLIIconDecoder.cpp::decode_pipeline` + `do_image_decode`，`g_trace_fallback=1` 默认启用）：

```
定位 → mode 0(质心+部分弧) 追踪解码 → 成功则返回
                                   → 失败则 mode 2(角点跳跃) 追踪解码 → 成功则返回
                                                                       → 失败返回 0
```

mode 0 先跑 → **HIT 零回归（构造保证）**，仅在 mode 0 失败时用 mode 2 追加机会。

**A/B 结果（centroid-only vs try-both）**：

| 方案 | 解码数 | 回归 | 净增益 |
|------|--------|------|--------|
| centroid-only | 19 | — | 基线 |
| **try-both（shipped）** | **31** | **0** | **+12** |

- **尝试顺序**：mode 0(质心) → mode 2(角点跳跃) → mode 3(反向起点，从 pos2 反向绕盾牌追踪)
- 7/7 HIT 全部解码
- 12 张新增全部输出正确码 `00000021040`，**无误报**

## 六、试过但被证伪的方案

### 6.1 法向匹配滤波 / 方向性质心（原 P0 建议）

**思路**：用沿框线法向的 1D 暗脉冲匹配滤波替换质心，期望角点处更稳。

**实测**（A/B，3 档参数）：
| tan_half | 净增益 |
|----------|--------|
| = frame_width | −5 |
| = 2×frame_width | −2 |
| = 全圆盘（≡质心） | −2 |

**证伪原因**：法向窄窗有"切向盲点"——曲率使框线偏离法线时，滤波锁到相邻数据模块并漂移；质心法的各向同性圆盘反而更稳。**保留代码（mode 1）但默认关闭。**

### 6.2 参数重试（更大半径/更细步长）

追踪失败时重试更大圆盘 + 更细步长。实测 **0 收益**（角点处更大半径反而更易抓到另一条边）。已移除。

### 6.3 放宽 63-bit BCH 纠错上限（err≤3 → err≤5）

**思路**：BCH(63, t=5) 可纠最多 5 错，当前只接受 ≤3。放宽到 5，配合 re-encode 校验防误纠。

**实测**：+7 解码（28→35），但其中 4 张产出错误码（`56355536032`、`41257208578`、`02132609360`，地面真值全部应为 `00000021040`）。

**证伪原因**：BCH 误纠正——接收字错误数 >5 时，Berlekamp-Massey 可能"纠正"到一个**不同的**合法码字，re-encode 校验通过但语义错误。**err≤3 的保守限制是必要的安全余量，不可移除。** 已回退。

### 6.4 mode 2 重试门控（按 fail_stage 跳过）

**思路**：mode 0 失败时根据失败阶段决定是否跑 mode 2，降低 try-both 拒绝路径开销。

**实测**：按 stage=2(trace) 门控导致 28→20（-8），丢失了 mode 2 通过不同弧角点救回 stage=5(bch) 失败的帧。已回退。

### 6.5 双通道角点精炼（two-pass corner refinement）

**思路**：finetune_corners 跑两遍，提高部分弧角点精度。

**实测**：28→23（-5），双重修剪移除了过多弧段数据。已回退。

### 6.6 定位置信度门控（locate confidence gating）

**思路**：根据 BSPatternMatch 匹配质量门控 mode 2/3 重试，低置信度时跳过以降低拒绝路径开销。

**实测**：BSPatternMatch ±10% 容差本身已是有力质量过滤——所有通过的定位匹配置信度均 ≥0.4，0 跳过的安全提升。阈值升至 0.7 时才跳过但丢失 5 张解码（HIT 回归）。**BSPatternMatch 已足够选择性，置信度门控无效。** 已移除。

### 6.7 放宽 BS 比例容差（±10%→±12%）

**思路**：放宽 BSPatternMatch 比例容差，覆盖低对比度/模糊帧，减少 locate-fail。

**实测**：放宽到 ±12% 产生大量误报（locate 在噪声中匹配到虚假"模式"）。地面真值确认仅 `00000021040` 为正确码。已回退。

## 九、性能与代价

### 9.1 解码正确性的代价

Try-Both 在 mode 0 失败的帧上多跑一次 mode 2 全流程（定位之后的 trace+corner+curve+decode）。拒绝路径约 2× 延时。

**缓解**：mode 2 仅在 mode 0 失败时触发；mode 0 的部分弧接受已能处理多数可救帧。后续可在定位置信度低时跳过 mode 2。

### 9.2 PC vs Android

PC（MSVC Release）<1ms/帧；Android 参考实现 10-144ms/帧（文件名标注）。PC 约快 50-100×。微优化（内存池、单次遍历、快速二值化等）主要针对 Android 端延时。

## 十一、第二阶段优化（2026-08）：P1 模型角点 + P2 直接采样 + 性能

> 测试集：207 张图（第二轮）+ 110 张图（第三轮），A/B 验证

### 11.1 P2 直接曲线采样（核心突破，+39~+84 解码）

**问题**：`do_curve_sample` 对 trace 点拟合三次多项式 `y=c₀+c₁x+c₂x²+c₃x³`，再在多项式上均匀分 span → 求弦长 → 重采样。多项式在弯曲边缘处会产生**振荡/过冲**，导致采样位置偏离实际模块中心。

**方案**（`CurveSampler.cpp::do_curve_sample_direct`，`g_direct_sample` 开关）：

跳过多项式拟合，直接从 trace 点做分段线性弧长参数化：
1. 沿 trace 点计算累积弦长 `cum_len[j] = cum_len[j-1] + sqrt(dx²+dy²)`
2. 按均匀弧长步长在 trace 点之间线性插值采样位置
3. 保留透视角校正逻辑

**优势**：
- 零多项式误差——采样位置精确跟随 trace 点轨迹
- 对不规则弯曲边缘更鲁棒
- 消除了 `do_curve_fit_with_coord_normalization` 的矩阵求逆失败（singular matrix）风险

**A/B 结果**：

| 测试集 | Baseline | P2 | 净增益 |
|--------|----------|-----|--------|
| 207 图（batch 1-7） | ~21 (10%) | **~105 (49%)** | **+84** |
| 60 图（早期 HIT） | 18 (30%) | **57 (95%)** | **+39** |

- **零回归、零误报**——所有新解码码字 = 地面真值
- P2 是单一项贡献最大的优化

### 11.2 P1 模型角点验证与回退

**11.2.1 形状验证器**（`ISLIIconDecoder.cpp::decode_pipeline`，`g_model_corners` 开关）

计算四角构成的四边形面积（鞋带公式）和对角线比。形状明显退化时（面积过小 / 对角线比极端）→ 用 locate 标记 + 几何模型预测四角替代 traced 角点。

**11.2.2 模型回退解码**（`decode_pipeline_model()`）

当所有 trace 尝试都失败时，跳过 trace 直接：模型预测四角 → 线性插值合成边框点 → P2 直接采样 → wave2bits → BCH。覆盖了 trace 彻底脱轨但 locate 成功的图像。

**11.2.3 自适应 Skip 阈值**

将固定 `prog0 < 60` 改为 `prog0 < frame_size * 3.5`（clamp [25,60]），小盾牌不再被错误跳过。例如 frame_size=9 时阈值=32，允许 58-dot 部分弧进入 mode 2 重试。

**A/B 结果**：
- trace 失败：Baseline 13 → Model **1**（12 张被救回到 BCH 阶段）
- 额外贡献：部分图像通过模型回退直接解码

### 11.3 性能优化：跳过冗余重试

**问题**：dot_num≥155（满周长）时 mode 0/2/3 产生几乎相同的角点，但仍跑 4 次完整管线。每张图耗时可达 200-328ms。

**方案**：`dot_num ≥ 140` 时判定为满周长 trace——边框已完整追踪，角点跳跃无益。直接跳过 mode 2 和 mode 3。仅对部分弧（100-139 dots）尝试 mode 2/3。

**效果**：满周长 BCH 失败图（占 90%）从 4 次管线减为 1 次，预期 **2-3× 加速**。

### 11.4 架构接口更新


## 十二、试过但被证伪的方案（第二阶段新增）

### 12.1 P3 亚像素模块细化

**思路**：在 wave2bits 中，对每个比特采样位置做 ±2 像素局部搜索，找波形值与阈值距离最大的位置。

**实测**：BCH 失败率零改善（99→99），且回归 1 张。**原因**：波形已经过低通滤波平滑，局部搜索与线性插值结果相同。已回退。

### 12.2 自适应局部阈值

**思路**：比特采样时用 70% 局部 min/max 中点 + 30% 线性斜坡替代纯线性阈值。

**实测**：net-1（丢失 MISS00101）。局部窗口内 min/max 受当前比特值主导，中点与线性阈值差异微小。已回退。

### 12.3 图像预处理（对比度拉伸 + 锐化）

**思路**：在 locate 前对全图做百分位对比度拉伸 + unsharp mask 锐化，增强模块边界。

**实测**：
- locate 前执行 → 大量 locate 失败（BS 模式匹配被干扰）
- locate 后执行 → trace 脱轨增多（锐化引入伪影）
- 已回退，代码保留（`g_preprocess=0`），供后续按需启用

### 12.4 Chase 软判决 BCH（在当前测试集上）

**思路**：翻转置信度最低的比特组合重试 BCH（已实现的 `g_chase_enable`）。

## 十四、第三阶段优化（2026-08）：短弧同步瞬态修复

> 测试集：110 张（测试集3，码 `03000000461`），PC 诊断 + per-curve bit-error 分析

### 15.1 诊断基础设施

新增 `test_data/test_diag.cpp`（批量）+ `test_data/test_dump.cpp`（单图波形 dump），以及解码器诊断接口（`ISLIIconDecoder.h`）：`islii_get_last_bch_err63`、`islii_get_last_wave63_ret`、`islii_get_last_dot_num`、`islii_get_last_received63`、`islii_get_last_bits63_raw`、`islii_set_max_bch_err63`。通过期望码字（`03000000461` -> encode_bch -> 期望码字）计算 per-curve Hamming 距离，精确定位错误来源。

### 15.2 根因：短弧同步位被起点瞬态毛刺锁定

**诊断**：99/106 失败在 BCH 阶段。Per-curve 分析显示错误集中在**短弧**（curve0/1，8-bit 边）。长弧 curve2 近乎完美。

**根因**：`wave2bits()` 同步检测"跳过前导暗、跳过首个亮游程"会锁定波形起点的 2-采样瞬态毛刺（边缘半模块/渐变），而非真正同步位。HIT00104 的 s=2（瞬态）而非 s=51（真同步），10 个 bit 采样整体移位 ~1 bit，短弧 8 bit 中 3-5 个错误。Android 参考实现能解码这些 HIT 图，说明其 bit 提取更稳。

**修复**（`Wave2Bits.cpp::wave2bits`）：鲁棒同步检测，跳过长度 < `0.4*len/(bit_num+2)`（≈0.4 bit 宽）的短游程，锁定真正同步游程。**带回退**：鲁棒结果跨度 < 75% 时回退原始首/尾游程检测。**零回归构造保证**：仅当首个游程 < 0.4 bit（瞬态）时与原始行为分歧。

## 十七、第六阶段优化（2026-08）：双阈值修复 corner 过渡区（核心突破）

> 测试集：cache2（519 张完整盾牌），码 `03000000461`。删除不完整盾牌后 408/410 失败在 BCH 阶段。

### 17.1 根因：corner 物理过渡区形成三层亮度

白底完整盾牌的 trace 成功（locate 0 失败、trace 仅 2 失败），但 **408/410 失败在 BCH**（波形/bit 提取）。Per-curve 分析：

- **c1 短弧（3-5 错误）**：波形头是 corner 物理过渡区（斜坡 103->160），头窗口（72 样本=1.7 bit）只含 85%K 亮模块（76）+ 过渡区，**漏掉 100%K 暗模块（22，在 bit 5）**-> 阈值偏高（th0=118，应 49）-> 亮模块被判暗 -> bit 翻转。
- 数据模式 `11111010`：前 5 bit 全亮，头窗口无论多大都只有亮模块。

**三层亮度问题**：暗（22）/ 亮（76）/ 过渡（103-160）。单一阈值无法同时分离三层：
- 原始阈值（~118）：分离亮/过渡 -> **sync 正确，但亮模块被判暗 -> bit 错**
- 百分位阈值（~49）：分离暗/亮 -> **bit 正确，但过渡区与亮模块合并 -> sync 错**（偏移 5 bit）

### 17.2 方案：双阈值分离 sync 检测与 bit 提取

**实现**（`Wave2Bits.cpp`）：

```cpp
// wave2bits 新增 bit_th 参数（默认 -1=用 th0/th1 ramp）
wave2bits(wave, len, +1, th0, +1, th1, 10, bits, conf, graph_name, 0, bit_th);

// bit 提取：bit_th >= 0 时用百分位阈值（扁平），否则用原始 ramp
double th_p = (bit_th >= 0) ? (double)bit_th : (th0 + th_step * dp);
```

`wave2bits63_1` 中，当头/尾窗口单极性（`h_min>50 && th0>80`，即无暗模块）时：
1. **sync 检测**（binarization + find sync runs）：用原始 th0/th1（分离过渡区与亮模块）
2. **bit 提取**：用全波形 p25/p75 百分位中点（分离暗 22 与亮 76）
3. **Chase 跳过**：`bits_decode` 检测 `g_wave_bitth_used` 标志时跳过 Chase（双阈值给出正确 bit，err≤3 无需 Chase；Chase 在改变后的 bit 上有 BCH 误纠 FP 风险）

### 17.3 A/B 结果（0 FP 0 回归 9/9 稳定）

|--------|--------|--------|------|-----|------|

| cache2 (519) | 109 | **113** | +4 | 0 | 0 |

### 17.4 FP 消除的 A/B 探索路径

| 配置 | cache2 | cache1 | 测试集3 | FP | 结论 |
|------|--------|--------|---------|-----|------|
| 原始（头尾阈值） | 109 | 136 | 14 | 0 | 基线 |
| 双阈值 + Chase | 116 | 138 | 17 | **1** | Chase 误纠 FP |
| 双阈值 + err≤2 + no Chase | 106 | 137 | 15 | 0 | 过严，cache2 回归 |
| **双阈值 + err≤3 + no Chase for bitth** | **113** | **138** | **15** | **0** | **最终方案** |

FP 链路：双阈值改变 c0/c1 bit -> err=4-5 -> Chase 翻转降到 err≤3 -> 命中错误合法码字 -> re-encode 通过 -> FP。解法：双阈值使用时跳过 Chase（err≤3 直接接受，无需 Chase）。

### 17.5 关键教训

1. **corner 过渡区是第三亮度层**（比亮模块更亮），单一阈值无法同时分离三层（暗/亮/过渡）。
2. **sync 和 bit 对阈值的需求不同**：sync 需分离亮/过渡，bit 需分离暗/亮 -> 双阈值是正解。
3. **Chase 在改变后的 bit 上有误纠风险**（BCH 在实际 err>t 时找到伪 err≤3 解）-> 需跳过。
4. 之前失败的单阈值方案（全波形/中间段/百分位）都是因为**混淆了 sync 和 bit 的不同需求**。

## 十九、第七阶段：c3 同步极性重试（BCH 校验裁决）

### 19.1 问题发现

对 977 张图的逐位分析发现一类系统性失败模式：**c3 长弧（23-bit，bits[40-62]）的半数据位出错（~11/23 ≈ 48%），但 c0/c1/c2 完全正确（0 错误）**。这在 cache1 中占了 **37 张图**（"c3-dominant" 模式）。

**根因**：c3 长弧有 2 条内部同步位，其极性（峰/谷）由 `match_sync_pos` 的 `auto_peak` 自动检测。检测公式 `(score[0]+score[spb-1])/2 < score[spb/2]` 在相邻数据位与同步位极性相同时被污染，导致极性判断错误 -> 同步位置偏移 -> 整段 bit 格点偏移 -> 大量错误。

### 19.2 方案设计

**BCH 校验裁决的同步极性重试**：

- 63-bit 自动极性解码失败（BCH err>3 或不可纠）时，逐一尝试 c3 的 4 种强制极性组合 `[0,0][1,0][0,1][1,1]`（0=谷, 1=峰）。
- 取 **BCH err 最小的合格组合**（min-err selection），真解码几乎总是 err 最低（通常 0），进一步降低 FP 风险。
- 零回归：仅在自动 BCH 失败时触发；接受标准与基线一致（err≤3 + re-encode 匹配）。
- 性能：仅重做 wave2bits63+BCH（复用已采样曲线），远轻于 trace/curve_sample。实测 ~0.07ms/image。

### 19.3 配套修复

1. **内存池清零**（`g_pool = new ...; memset(0)`）：消除未初始化内存导致的**非确定性解码**（同一输入，不同进程/运行输出不同结果）。这是 0 FP 的基础——先确保可复现，才能保证 A/B 的可靠性。

2. **g_wave_bitth_used 每调用复位**（`do_wave2bits63` 开头置 0）：原代码从不复位，多帧重试时前一帧的 bit_th 状态泄露到下一帧，导致 Chase 错误跳过或运行。c3 极性重试会多次调用 `do_wave2bits63`，比之前更需要可靠的 per-call 状态。

3. **禁用 63-bit Chase 软判决**：Chase（g_chase_enable=1）在 err=4..5 时有 **BCH 误纠 FP**（实测 cache2 2FP 解码为错误码 00022089496）。`g_wave_bitth_used` 修复 + 内存池清零后 Chase 行为可复现且一致，暴露了该 FP。且 Chase 净收益为 0（清零池上实测 0 差），c3 重试 +88 远超 Chase 的贡献。

4. **112-bit BCH 纠错上限收紧**（7→3）：与 63-bit 保持同一安全余量（err≤3），消除 112-bit 误纠风险。

### 19.4 A/B 验证（0 FP 0 回归 9/9 稳定）

| 测试集 | c3-retry OFF | **c3-retry ON** | c3r 收益 | 回归 | FP |
|--------|------------|---------------|------|-----------|----|
| 测试集3 cache (110) | 15 | **15** | 0 | 0 | 0 |
| cache1 (348) | 138 | **183** | **+45** | 0 | **0** |
| cache2 (519) | 113 | **156** | **+43** | 0 | **0** |
| **合计** | 266 | **354** | **+88** | 0 | **0** |

9/9 确定性稳定（连续 3 次运行结果完全一致），0 FP（全部解码为 03000000461），0 回归，性能 ~0.07ms/image。

### 19.5 全部优化累计

| 优化 | 测试集3 | cache1 | cache2 |
|------|---------|--------|--------|
| 短弧同步修复 | 4->14 | - | - |
| poly try-both | - | +27 | - |
| 63-bit Chase（已退役） | - | (+5) | - |
| calc_center_shift/amend_center 边缘修复 | - | +1 | +2 |
| sample_line/sample_one_curve 越界修复 | crash 修复 | - | crash 修复 |
| 双阈值（sync=原始, bit=百分位） | +1 | +2 | +4 |
| **c3 同步极性重试** | - | **+45** | **+43** |
| **累计（对最终基线：model=1,direct=1）** | **4->15** | **27->183** | **->156** |

**最终发布得分**：测试集3 15, cache1 183, cache2 156。总计 354/977 (36.2%)。

### 19.6 经验总结

1. **c3 长弧同步极性自动检测不可靠**：相邻数据位与同步位极性相同时会污染 `auto_peak` 判决。BCH 校验裁决的 4 组合 min-err 重试是零回归、零 FP 的正解。
2. **内存池清零消除非确定性**：`new` 分配的 POD 数组含随机值 -> 非确定性解码 -> A/B 不可信。**0 FP 的前提是先确保可复现。**
3. **Chase 软判决的安全边界需在"可复现"前提下重评估**：原测量"0 FP +5"是在非确定性 + stale-state 下的结果。清零池 + 状态修复后 Chase 净收益 0 且误纠 2FP -> 决策退役。这并不改变之前 A/B 的结论（当时确实 +5/0FP），但说明**非确定性会掩盖问题**。
4. **min-err selection > first-success**：4 种极性组合中取 BCH err 最小的（而非第一个命中的），真解码 err 几乎总是最低（通常 0），进一步降低 FP 风险。

## 二十、第八阶段：移除 NEON float 滤波（消除手机 vs PC 位差异）

### 20.1 问题发现

cache4 (413张真机采集图) 在 PC 端（Windows/MSVC/标量双精度）测试 **0 FP**，但用户报告 Android 真机 **FP>0**。

排查路径：
1. PC 端 c3-retry A/B 验证：cache4 上 noC3=258, c3r=271, 0 FP, 0 回归。→ FP 非算法逻辑问题。
2. 确认手机 vs PC 代码差异：Android NDK 定义 `__ARM_NEON` 启用 `Filter.cpp` 中的 NEON 分支；Windows MSVC 走标量分支。
3. 审查所有 NEON 代码（6 个文件）：ISLI icon 盾牌解码器仅在 `isli/Filter.cpp` 使用 NEON（`linecode/` 下的 ISLILineDecoder/GaussianBinarization 属于一维条码解码器，不影响盾牌解码）。

### 20.2 根因：NEON float 精度 ≠ 标量 double 精度

`do_low_pass_filter` (27 抽头低通滤波器) 的输出直接送入 wave2bits 二值化 -> 位提取 -> BCH。NEON 路径与标量路径的关键差异：

| 维度 | NEON (`__ARM_NEON` 分支) | 标量 (`#else` 分支，PC 端) |
|------|-------------------------|------------------------|
| 累加精度 | float (32-bit, ～7 位有效数字) | double (64-bit, ～15 位有效数字) |
| 缩放因子 | `1.0f / 1.208f` (float, 编译期计算) | `1.208` 除数 (double, 运行时) |
| FMA | `vmlaq_f32` 单次舍入 | 乘法+加法各舍入一次 |
| 系数 | `(float)lp_filter_coef[i]` | `double lp_filter_coef[i]` |

单一像素输出差异最多 ±1，但这一差异**改变 binarization 阈值** → 改变处于临界波形的比特判定 → 多个比特错误 → BCH 找到距离 ≤3 的**错误码字**（误纠 FP）。

### 20.3 修复

**完全移除 `Filter.cpp` 中的 `#ifdef __ARM_NEON` 分支**——手机与 PC 统一使用标量 double 路径。性能影响可忽略：27 抽头 × ～500 样本/边 × 4 边 ≈ 54K 乘加运算 ≈ **0.01ms/image**，远低于 trace/curve_sample 耗时（总解码 ～50ms）。

### 20.4 验证

| 测试集 | noC3 | c3r | FP | 回归 | 确定性 |
|--------|------|-----|----|------|------|
| cache (110) | 15 | 15 | 0 | 0 | ✓ |
| cache1 (348) | 138 | 183 | 0 | 0 | ✓ |
| cache2 (519) | 113 | 156 | 0 | 0 | ✓ |
| **cache4 (413)** | **258** | **271** | **0** | **0** | **✓** |

**总计：354/977 (36.2%) 解码，0 FP 0 回归，全平台 bit-exact 一致。**

### 20.5 经验总结

1. **FP 排查必须覆盖手机 vs PC 的所有代码路径差异**。NEON intrinsics 分支仅在手机上执行，PC A/B 无法覆盖。
2. **浮点精度差异在图像处理的"传递"中会被放大**：+1/-1 像素差异 → 阈值偏移 → 临界比特翻转 → BCH 误纠码字。
3. **低通滤波用 double 精度远过剩，但保证 bit-exact 可复现**。`do_low_pass_filter` 在总解码耗时中占比 <0.02%，用 double 不构成性能瓶颈。
4. 若未来确实需要 NEON 加速此函数，应**先与标量 double 输出逐像素做交叉验证**（全测试集 diff=0），再启用量产。

## 二十一、第九阶段：cache5 真机 vs PC 一致性验证（68719476735 全1 FP 定位）

### 21.1 现象

cache5（134 张真机采集图，文件名内嵌手机解码结果 `<code>_<ms>ms`）手机端分布：

| 手机结果 | 数量 | 说明 |
|----------|------|------|
| 03000000461 | 82 | 正确 |
| 68719476735 | 12 | **FP**（= 2^36−1，36 位数据全 1，退化码字） |
| none | 40 | 未解码 |

用户报告"解码出现错误结果 68719476735"。要求在 PC 下验证是否与手机一致。

### 21.2 PC vs 手机 一致性结论：**不一致**

PC（当前 `isli/` 源码，shipped 配置 c3r）在 cache5 上：

| | PC (shipped c3r) | 手机 (cache5) |
|---|---|---|
| 解码数 | 100 | 94 |
| 正确 | 100 | 82 |
| FP | **0** | **12**（全为 68719476735） |

12 张手机 FP 图在 PC 上的表现：
- **3 张**（HIT00093 / HIT00103 / HIT00113）：PC **正确解码**为 03000000461，手机却输出全1 FP —— 同一帧同一算法结果直接矛盾。
- **9 张**：PC 解码失败（none），手机输出全1 FP。

输入 PGM 帧完全相同（PC 读取的就是手机采集保存的同一帧），结果却不同 ⇒ 手机运行的不是当前 `isli/` 源码。

### 21.3 根因：手机运行的是过期快照 `isli_080401`（仍含 NEON float 滤波）

仓库内存在三份 isli 解码器副本：`isli/`（当前修复版）、`isli_0804/`、`isli_080401/`（带时间戳的旧快照）。CMakeLists.txt 编译的是 `isli/`，但手机端实际部署的 .so 来自旧快照状态。对比 `isli_080401` 与当前 `isli/`：

| 项 | `isli_080401`（手机实际运行） | 当前 `isli/`（已修复） |
|----|------------------------------|----------------------|
| `Filter.cpp` NEON float 分支 | **有**（`float32x4_t`/`1.0f/1.208f`） | **已移除**（标量 double） |
| `g_chase_enable` | 1（启用） | 0（禁用） |
| `g_max_bch_err112` | 7 | 3 |
| `g_c3_retry` | 无（未实现） | 1 |
| 内存池 `memset` 清零 | 无（非确定） | 有 |

NEON float 分支仅在 `__ARM_NEON`（手机）下编译，PC（MSVC）走标量 double。float vs double 的 ±1 像素滤波差异经 二值化→wave2bits→BCH 传递，在 12 张临界图上把接收比特推到全1码字（68719476735）的 t≤3 范围内，BCH 误纠为全1 ⇒ FP。

### 21.4 决定性实验：配置无关，NEON 是唯一成因

为排除"Chase/err112 配置导致 FP"的假设，在 PC 标量路径上用**旧手机配置**（chase=1, err63=3, err112=7, c3_retry=0）跑 cache5：

| PC 配置 | 解码数 | FP | 全1(68719476735) |
|---------|--------|----|----|
| shipped c3r (chase=0,err=3,c3=1) | 100 | 0 | 0 |
| err5 上限 (chase=1,err=5,c3=1) | — | 8 | 0 |
| **旧手机配置 (chase=1,err=3,err112=7,c3=0)** | **99** | **0** | **0** |

**PC 在任何配置下都从不输出 68719476735**（`code=68719476735` 出现 0 次）。旧手机配置在 PC 标量上 0 FP ⇒ 全1 FP 与 Chase/err112 配置**无关**，纯粹由 ARM NEON float 滤波精度差异造成。当前 `isli/` 已移除 NEON 分支 ⇒ 修复已在源码中。

### 21.5 修复与验证

- **无需改算法**。修复已在当前 `isli/` 源码中（NEON 移除 + Chase=0 + err112=3 + c3_retry=1 + 内存池清零）。CMakeLists.txt 已编译 `isli/`。
- **行动项**：用当前源码**重新编译 Android SDK 并重新部署到手机**，cache5 预期 0 FP。
- **清理建议**：删除过期快照 `src/main/cpp/isli_0804/`、`isli_080401/`（CMake 不引用，仅造成混淆）。
- 回归确认（shipped c3r 配置不变）：cache1=183 / cache2=156 / cache4=271，均 0 FP 0 回归。

### 21.6 经验总结

1. **多份源码副本是部署陷阱**。`isli_0804`/`isli_080401` 快照与 `isli/` 并存，导致手机实际运行过期代码而 PC 验证的是新代码——"源码已修但 FP 仍在"的假象。
2. **真机 FP 验证的第一步应是确认部署的 .so 来自哪份源码**，而非先怀疑算法。
3. **全1（2^36−1）/ 全0 退化码字**是位提取失败（NEON 精度差异/阈值崩溃）的典型签名，BCH 一致性校验无法拦截（全1是合法码字）。
4. **PC 永远无法复现 `__ARM_NEON` 分支的差异**——必须交叉验证 ARM 构建的滤波输出与 PC 标量逐像素 diff=0。

### 21.7 退化码字过滤（防御性 guard，针对 68719476735）

即便根因是过期 NEON 快照（重编译即解），仍增加防御性 guard：**拒绝全1/全0 退化数据字**，确保任何未来位提取差异都不会再产生此类 FP。

**实现**（`ISLIIconDecoder.cpp`）：
- `bits2string`（63 位，36 数据位）/ `bits2string2`（112 位，63 数据位）由 `void` 改为返回 `int`：计算出数据值 `val` 后，若 `val == 0`（全0）或 `val == 2^36-1 = 0xFFFFFFFFF = 68719476735`（63 位路径）/ `2^63-1`（112 位路径），且 `g_reject_degenerate=1`，则返回 0（拒绝），调用方不视为解码成功。
- 全局开关 `g_reject_degenerate`（默认 1）+ setter/getter，支持 A/B。
- 真实盾牌码为混合比特，数据字不可能是全同 -> 过滤安全；BCH 一致性校验无法拦截（全1/全0 均为合法码字，re-encode 必然匹配）。

**验证**：
1. **自检 `islii_selftest_degenerate_guard()`**：合成全1 `{0x0F,0xFF,0xFF,0xFF,0xFF}` 与全0 数据字，验证 guard ON 时 `bits2string` 返回 0（拒绝，code="68719476735"/"00000000000"）、OFF 时返回 1（放行）。全 5 测试集均 PASS。
2. **A/B（guard ON vs OFF，shipped c3r）**：cache=15/15、cache1=183/183、cache2=156/156、cache4=271/271、cache5=100/100，guard OFF 全1=0，回归=0，FP=0。

PC 端 guard 从不触发（NEON 已移除，PC 永不产生全1），故 guard ON == guard OFF，0 回归 0 FP。guard 仅在位提取差异（如手机旧 NEON 快照）产生全1 时生效，把 68719476735 FP 转为"未解码"而非"误解码"。

**结论**：guard 是纯防御性措施（PC 端无收益无回归），在手机端为 68719476735 FP 提供兜底拦截。配合 21.5 的重新编译部署，双保险消除该 FP。

### 22.5 优化点 1：corner_score 预计算平滑区域（POSITIVE，性能 +33%，bit-exact）

**瓶颈定位**（阶段计时，cache6 累计）：corner 阶段占 **52.2%**（trace 17.5%, curve 25%, wave 4.7%, bch 0.6%）。`fine_tune_corner_coord` 对每个黑白边界候选点调用 `corner_score`，后者在 (2r2+1)² 窗口内每像素调 4 次 `smooth()`（3×3 均值，9 读），即每窗口像素 36 次像素读 -> 角点微调是头号热点。

**bit-exact 保证**：S 即 `smooth()` 的逐位相同输出（整数算术，9 像素求和 +4 后 /9）；`corner_score_S` 的 Ix/Iy/sumIx²/.../Harris 响应与原 `corner_score` 完全一致。边界语义保持（窗口越界=越出图像有效区，返回 0）。

1. **多线垂直平均采样**（`do_curve_sample_direct` 沿法线平均 2P+1 条 3×3）：perp=2 总解码 1227→1218（-9），perp=3→1197（-30）。根因：盾牌边框薄，垂直平均混入背景/邻位 -> 冲淡比特信号。0 FP 但解码率下降，**否决**。
2. **min_span 0.75→0.65**（sync 跨度阈值放宽）：diag(noC3) 显示 +12，但 shipped c3r 下 1227→1179（**-48**，cache2 -21 cache3 -30）。根因：放宽跨度改变 sync 位置检测，与 c3_retry 极性重试交互负面。0 FP 但解码率下降，**否决**。教训：A/B 必须在 shipped 配置（c3r）上做，noC3 信号会误导。

3. **precompute_smooth 可分离 3×3 均值**（滚动列和+行和，9 读/像素->~2 读/像素，bit-exact）：意图加速 corner 阶段 precompute_smooth。A/B（cache6，3×back-to-back）：corner 838K(baseline) vs 843K(new) us，**中性**（无加速）。根因：原 9 读循环的 3×3 邻域全在 L1（局部性好），编译器已充分优化；可分离版增加算术与依赖链，抵消了读数减少。bit-exact（1227 解码 0 FP）但无性能收益，**否决**。教训：L1 局部性好的小窗口 box filter，可分离优化常无效（与 22.5 的大窗口预计算不同）。

### 22.7 关键发现：间歇性非确定性 FP（阻断可靠 A/B，需优先修复）

**现象**：cache2 的 MISS00138（borderline，孤立解码 bch63=4 稳定失败）在 shipped c3r 配置下**间歇性**解码为 `52512886016`（FP）。同一二进制同一输入，跨进程运行结果不同（某批 6/6 FP，某批 1/5 FP）；孤立单图解码则稳定失败。

**性质**：
- 取决于进程内**先验解码的堆布局**（解码很多图后才触发）-> 典型**未初始化内存读**特征。
- 每次解码 init/uninit 重建+清零内存池，BCH 表也重建 -> 非池/BCH 内残留，而是**未初始化栈/堆读**（位提取路径）。
- /RTCu（/Od 下）不复现（/Od 改变行为）；ASan 无 buffer-overflow（ASan 不查未初始化读）。
- 位翻转发生在 BCH 之前（bit 提取阶段），bch63 在 4 与 ≤3(误纠) 间漂移。

**归因**：非我本次 corner_score_S 引入（数学 bit-exact，无新增堆读，smooth_patch 不溢出——已加探针验证 sw\*sh ≤ 192²）。疑为**既有**未初始化读（"first complete" 基线的 0-FP 可能是侥幸运行）；位提取/曲线采样路径存在某处 buffer 读前未完全写。

**影响**：威胁 0-FP 硬性要求（borderline 图可能间歇 FP）；使 A/B 信号含 ±1~2 噪声，细粒度优化（如滤波对称）无法干净验证。

**下一步建议**：需在 Linux 用 `valgrind --track-origins=yes` 或 clang `-fsanitize=memory`（MSan）定位未初始化读；或逐函数审计位提取/曲线采样路径的 buffer 分配与读取范围。修复前不宜再做依赖 ±1 精度的 A/B。

### 22.8 滤波对称优化（等价但暂缓）

低通滤波系数对称（coef[p]==coef[26-p]），可用 14 乘代替 27 乘。孤立解码验证 sym14 与 orig27 逐图等价（MISS00138 同为 bch63=4 失败）。但因 22.7 的非确定性，多配置 A/B 含 ±1 噪声（cache2 出现 1 次 FILTER-FLIP，实为非确定性而非滤波差异）。**暂缓**：待非确定性修复后再干净 A/B；预期收益 ~8%（curve 阶段滤波子热点）。

### 22.9 非确定性部分修复：bch_alloc 清零（FP 频率大幅下降）

**定位**：通过 corners/curve/bits 校验和二分（diag 工具），确认 MISS00138-frame1 的 **corners 与 curve(波形) 跨运行完全一致**，但 BCH 结果漂移（bch63 在 4=失败 与 3=FP 间）。即非确定性在 **curve 之后**（wave2bits→BCH）。

**根因（主要）**：BCH 表每次解码由 init_bch 用 `bch_alloc`(=malloc，无清零) 重建并 free，表内残留依赖先验解码的堆布局；decode_bch 读取未完全初始化的表项 -> 同一 bits 跨运行得到不同 err -> 临界图(bch≈4) 偶尔落入 err≤3 误纠为另一合法码字(FP)。

**修复**（`bch.cpp::bch_alloc`）：malloc 后 `memset(0)`。所有 BCH 缓冲(a_pow_tab/a_log_tab/mod8_tab/ecc_buf/cache/syn/elp/poly_2t 等)均经 bch_alloc，故全量清零。

**效果**：FP 频率从 ~高频(某批 6/6 run)降至 ~1/10~1/20 run（仅 MISS00138-frame1 一张临界图）。解码数不变（15/183/156/113/271/100/389）。bit-exact 于确定性情形（清零后再 compute，最终表不变）。

**残留**：~5-10% run 仍有 1 FP（同一临界图）。疑为 curve 之后的另一未初始化读（wave2bits 罕见分支或 trace 罕见路径），因极罕见(<1/40)无法在 Windows 捕获，**仍需 Linux MSan/valgrind 彻底定位**。

### 22.10 非确定性根因彻底定位与修复：bits 数组未初始化读（MSan，FP->0，0 回归）

**定位方法**：在 Linux 服务器（172.16.2.111，clang 10）用 `clang++ -O1 -g -fsanitize=memory -fno-omit-frame-pointer`（MSan）构建纯 C 风格探针（避免 libstdc++ 未插桩的 std::string/vector 误报）。MSan 首次命中即指向真正的未初始化读：

```
use-of-uninitialized-value
    #0 compact_bits2(...) ISLIIconDecoder.cpp:458
    #1 bits_decode2(...)  ISLIIconDecoder.cpp:511
    #2 decode_pipeline    ISLIIconDecoder.cpp:762
```

**根因**（**真正根因，非 BCH 表**）：`do_wave2bits63` / `do_wave2bits112` 在某条曲线过短时 `break` 早退并返回 0，但调用方仍**无条件**对**未完全填充的 bits 数组**执行 BCH 解码。三处调用点同病：

1. `try_decode63`（63-bit 主路径，line 683）：`unsigned char bits63[112];` **未初始化**，`do_wave2bits63` 失败后仍 `bits_decode(bits63, ...)`。
2. `decode_pipeline` 112-bit 回退（line 759）：`unsigned char bits112[112];` 未初始化，`do_wave2bits112` 失败后仍 `bits_decode2(bits112, ...)`。
3. `decode_pipeline_model` 63+112-bit（line 840）：`unsigned char bits[112];` 未初始化，wave 失败后仍 `bits_decode` / `bits_decode2`。

`compact_bits`/`compact_bits2` 逐位读 `bits[k]`（k=0..62 / 0..111）。当 wave 失败、bits 仅部分填充时，未写字节为**栈上垃圾**，其值依赖进程内先验解码的堆/栈布局 -> 同一二进制同一输入跨运行结果不同 -> 临界图(MISS00138-frame1, bch≈4) 偶尔栈垃圾恰好构成 err≤3 的另一合法码字(52512886016) -> 间歇性 FP。这与 22.9 的 BCH 表清零修复正交：BCH 表清零消除了 BCH 表内残留，但 bits 数组本身的栈未初始化读是独立且更主要的根因（22.9 后仍残留 ~5-10% 即因此）。

**修复**（`ISLIIconDecoder.cpp`，三处统一）：
- `bits`/`bits63`/`bits112` 声明即零初始化 `= {0}`（防御性，使失败路径确定化为全 0）；
- BCH 解码加 wave 返回值短路守卫：`g_last_wave63_ret && bits_decode(...)`、`g_last_wave112_ret && bits_decode2(...)`（wave 失败时跳过无意义的 BCH，既杜绝未初始化读又省计算）。

wave 成功时（ret=1）4 条曲线已填满 bits，bits_decode 读到的全是已初始化数据；wave 失败时跳过，bits_decode 不再执行。结构上根除该路径的未初始化读。

**A/B 验证**（Linux clang -O2，shipped c3r 配置，全 7 测试集）：

| 测试集 | 解码(before) | 解码(after) | FP(before) | FP(after) |
|--------|-------------|------------|-----------|-----------|
| cache | 15 | 15 | 0* | 0 |
| cache1 | 183 | 183 | 0* | 0 |
| cache2 | 156 | 156 | 间歇 52512886016 | 0 |
| cache3 | 113 | 113 | 0* | 0 |
| cache4 | 271 | 271 | 0* | 0 |
| cache5 | 100 | 100 | 0* | 0 |
| cache6 | 389 | 389 | 0* | 0 |
| **合计** | **1227** | **1227** | 间歇 | **0** |

(* 单次运行的 0 FP 不能反映间歇性；before 的真实状态是 ~5-10% run 出现 1 FP。)

- **MSan**：全 7 测试集 0 例 `use-of-uninitialized-value`（修复前 cache2 首图即命中 compact_bits2）。
- **确定性**：cache2 连续 15 次 run 全部 FP=0、0 次 52512886016（修复前 ~1/10~1/20 run 出现）。
- **回归**：解码数逐测试集不变（1227->1227），0 回归。损失的仅是 wave 失败时从栈垃圾偶然产生的错误码（即 FP 本身），无任何真解码丢失。

**结论**：22.7 提出的阻断性非确定性问题彻底解决。A/B 信号不再含 ±1~2 噪声，后续细粒度优化（如 22.8 滤波对称）可干净验证。0 FP 硬性要求达成。

## 二十三、第十一阶段：span 放宽重试（try-both fallback，+16 解码，0 FP 0 回归）

> 方向：解码率算法优化。测试集：cache1-6 + 测试集3（共 2519 图），PC MSVC 验证（与 Android bit-exact，见 20.4/22.10）。

### 23.1 背景：直接下调 min_span 被否决（22.6.2）

`Wave2Bits.cpp` 同步检测在 robust 跨度 > `g_min_span`(0.75) 时用 robust sync，否则用原始 sync（line ~153-160）。22.6.2 实测直接下调 `g_min_span` 0.75->0.65 在 shipped c3r 下 **1227->1179（-48）**：低阈值移动了 robust/原始 sync 切换边界，对原本合格同步的另一批图产生回归。但 diag 同时显示放宽跨度对部分短跨度波形有益（0.70 FP-safe）。

**矛盾**：放宽跨度对 A 批图有益、对 B 批图有害，单一阈值无法兼顾。

### 23.2 方案：try-both fallback（0.75 优先，0.70 兜底）

不直接下调 `g_min_span`，而是 **0.75 整条解码失败后，放宽到 0.70 重试一次**。0.75 优先 -> 原解码路径完全不变（零回归构造保证）；0.70 fallback 仅在 0.75 失败时追加一次机会，且只在失败图上付出额外延时。

**实现**（`ISLIIconDecoder.cpp` + `Wave2Bits.cpp`）：

- 新增 `g_span_retry` 开关（默认 1）+ `SPAN_RETRY_FALLBACK=0.70`，setter/getter `islii_set_span_retry`/`islii_get_span_retry`。
- 抽取 `try_full_decode` lambda（63-bit auto + c3_retry + 112-bit 回退）供两条路径复用。
- `decode_pipeline`：`try_full_decode(0.75)` 失败后，若 `g_span_retry && islii_get_min_span() > 0.70`，临时 `islii_set_min_span(0.70)` 调一次 `try_full_decode("(span)")`，立即恢复 0.75。
- `decode_pipeline_model`：`span_list[2]={0.75, 0.70}` 循环，成功/退出均恢复 `span_list[0]`。
- `Wave2Bits` 新增 `islii_get_min_span()` getter（`g_min_span` 为 static，跨文件访问需要）。

**零回归保证**：fallback 仅在 0.75 整条失败（含 c3_retry + 112-bit）后触发，且 0.75 路径行为不变；`min_span` 在 fallback 后立即恢复，不影响下一图。

### 23.4 配套否决：c3-localized err≤5 guard（no-op）

### 23.5 经验总结

1. **单一阈值矛盾的解法是 try-both，而非调阈值**：放宽 min_span 对 A/B 两批图相反效果时，0.75 优先 + 0.70 兜底兼顾两端，零回归。
2. **fallback 代价仅在失败图上**：与直接下调阈值（影响所有图）不同，try-both 只对 0.75 失败的图多跑一次，吞吐几乎不受影响。
3. **22.6.2 的教训仍然成立**：A/B 必须在 shipped 配置（c3r）上做。本次 span_retry 的 +16 是在 c3r 基线上叠加；22.6.2 直接调 span 在 c3r 下 -48 正是因为与 c3_retry 交互负面。try-both 避开了该交互（0.75 路径含 c3_retry 不变）。

## 二十四、第十二阶段：c2+c3 联合同步极性重试（+135 解码，0 FP 0 回归，最大单项收益）

> 方向：解码率算法优化。测试集：cache1-6 + 测试集3（2519 图），PC MSVC 验证。

### 24.1 诊断：c2+c3 dominant 是最大失败桶（810 图）

扩展 `test_diag` 新增 c2-dominant / c2+c3-dominant 统计（c3_retry=0 诊断配置），全 7 测试集：

| 失败模式 | cache | cache1 | cache2 | cache3 | cache4 | cache5 | cache6 | 合计 |
|----------|-------|--------|--------|--------|--------|--------|--------|------|
| c3-dominant (仅c3错) | 0 | 39 | 0 | 0 | 7 | 0 | 20 | 66 |
| c2-dominant (仅c2错) | 0 | 1 | 0 | 0 | 4 | 1 | 21 | 27 |
| **c2+c3 dominant (两长弧均错)** | **61** | **120** | **277** | **242** | **89** | **6** | **15** | **810** |

c2+c3 dominant（c0+c1≤3 且 c2+c3≥10，短弧正确、两长弧均大错）是**最大失败桶**（810 图，远超 c3-dominant 66）。c3_retry 仅重试 c3（c2 自动），对这类"两长弧极性均误"无效--c3 强制极性虽对，c2 自动仍错 -> BCH err 仍 >3。

### 24.2 根因：c2 长弧与 c3 同理的极性自动检测污染

c2（24-bit 长弧）与 c3（23-bit 长弧）结构相同：各 2 条内部同步位，极性由 `match_sync_pos` 的 `auto_peak` 自动检测。19.1 已证 c3 的 auto_peak 被相邻数据位污染 -> 极性误判 -> 整段 bit 格点偏移 -> 大量错误。c2 同病，但此前无重试。

c2+c3 dominant 正是"两长弧极性均误"的签名：短弧（c0/c1，无内部同步位极性检测）正确，两长弧各自 ~半数位错（c2 ~12/24、c3 ~11/23）。

### 24.3 方案：c2+c3 联合 16 组合极性重试（min-err 裁决）

**实现**（`ISLIIconDecoder.cpp`）：
- `try_decode63` 扩展 c2 极性参数（`c2fp1/c2fp2`，经 `islii_set_c2_force_peak`，-1=自动）。
- `try_full_decode` 在 c3_retry 失败后追加**联合重试**：枚举 c2×c3 各 4 组极性共 16 组合，取 BCH err 最小的合格组合（err=0 提前退出）。新增 `g_c2_retry` 开关（默认 1）。
- 调用顺序：63-bit auto → c3_retry(4, c2自动) → **c2c3联合(16)** → 112-bit 回退。

**零回归保证**：联合重试仅在 auto + c3_retry 均 BCH 失败后触发；接受标准与基线一致（err≤3 + re-encode 匹配）。成功解码（auto/c3_retry 命中）零性能影响--联合重试只在失败图上付出 16 次 wave2bits63+BCH。

- 135 张新增全部输出正确码 `03000000461`（0 FP），0 回归，0 码字变更。

### 24.5 cache2 +0 的诊断价值

cache2 有 277 张 c2+c3 dominant 却 **0 rescued**--证实其长弧失败是**真波形退化**（bit 真错），非极性误判。强制任何极性组合都无法把 err 降到 ≤3，故 0 FP（无伪纠解空间）。这与 22.2 的 cache2 err>5=282（最大 err>5 桶）一致：cache2 瓶颈是波形 SNR，极性重试无能为力。反证 c2_retry 的 FP 安全性--真退化图不会被误纠。

### 24.6 经验总结

1. **c2 与 c3 同病同方**：两长弧结构相同（2 同步位 + auto_peak），极性自动检测同样被污染。c3_retry 验证了机制，c2c3 联合重试把收益从 c3 单弧扩展到 c2+c3 双弧。
2. **联合 16 组合 subsume 单弧重试的边界**：c2+c3 dominant 需两弧同时强制极性，单弧重试（c3_retry）因另一弧自动仍错而失败。联合枚举是覆盖该模式的唯一方式。
3. **极性重试的收益上限 = 极性误判占比，非全部长弧失败**：cache2 277 张 c2+c3 dominant 0 rescued，说明"两长弧均错"≠"两长弧极性均误"。极性重试只救极性误判部分，真退化需波形增强（多帧平均/ROI 预处理）。
4. **min-err 选择 + err=0 提前退出**：16 组合中真解码 err 几乎最低（常 0-3），min-err 选真解避免伪纠解抢先命中；err=0 提前退出兼顾性能。

## 二十五、第十三阶段：c2+c3 同步位置偏移重试（+29 解码，0 FP 0 回归）

### 25.1 背景：极性重试对 cache2/c2+c3 dominant 完全失效

第二十四阶段的 c2+c3 联合**极性**重试对 cache2 的 277 张 c2+c3 dominant 失败 **0 rescued**（24.5），结论是"真波形退化，极性重试无能为力，需波形增强（ROI 预处理）"。本阶段先验证 ROI 预处理，再深挖根因。

**ROI 预处理验证（已否决）**：考虑在 `do_curve_sample_direct` 采样后对长弧波形做局部对比度拉伸。但诊断发现所有失败长弧波形**满对比度**（mid-arc span 110-113，与头尾一致），无对比度坍塌、无同步失败（w63=0 跨全 cache 为 0）。且 Wave2Bits 阈值是对比度自适应的（`mean_of_peak2vally`=(min+max)/2、bit_th=百分位），**线性对比度拉伸是 no-op**（尺度不变）。ROI 预处理 0 收益，不可发布。

### 25.2 根因：同步**位置**错位（非极性、非 SNR）

对 cache2 失败图逐位比对 `got` vs `expected`（关全部重试，单次 auto）：

- **c2 = 精确 1 比特整体移位**：`got == exp >> 1`（整段 24 bit 系统性右移 1 位）。信号满对比度、跨图确定性复现。
- **c3 = 单同步位错位**：7 个错误集中在 sub2(3)+sub3(3)+sub1(1)，与 `sync_pos2` 偏移影响 sub2+sub3 一致。

根因是 `match_sync_pos` 锁定到**错误相邻峰/谷**致同步位偏移 1 比特，整段/子段比特中心系统性移位。`force_peak`（极性重试）只改峰/谷**极性**不改**位置**，故对位置错位 +0--这解释了 24.5 的 cache2 +0：失败是位置错位而非极性误判。

### 25.3 方案：比特中心相位偏移（非边界偏移）

**机制选型**：首试"同步位边界偏移"（`sync_pos1 += off*sample_per_bit`）--失败：移动边界破坏子段划分，子段过短（span<0.75）或检测到错误 run，36 组合中仅 (0,0)/(1,0) 有输出，A/B +0。

**正确机制--比特中心相位偏移**（`Wave2Bits.cpp`）：不动 `sync_pos1/sync_pos2` 边界，对每个子段的比特采样中心施 ±1 比特平移：
```
dp = s + 0.5*det + i*det + phase_off * det   // phase_off∈{-1,0,+1}
```
- `phase_off` 经 `wave2bits` 新增参数传入，带越界 clamp。
- 3 子段相位映射：sub1=`sync1_off`、sub2=`(sync1_off+sync2_off)/2`、sub3=`sync2_off`（sync_pos1 偏移影响 sub1+sub2，sync_pos2 影响 sub2+sub3，sub2 取均值，BCH t=5 容忍残余误差）。
- 新增全局 `g_c2_sync1_off/g_c2_sync2_off`、`g_c3_sync1_off/g_c3_sync2_off` + setter/getter。

**重试编排**（`ISLIIconDecoder.cpp`，try_full_decode 第 2c 步，c2c3 极性重试后、112-bit 回退前）：
- 每弧 6 种非零偏移 `{1,0},{-1,0},{0,1},{0,-1},{1,1},{-1,-1}`（单同步±1 + 整体±1），c2×c3 联合 36 组合，auto 极性，min-err 选择，err==0 提前退出。
- 新增 `g_pos_retry`（默认 1）开关。

**收紧到 err≤2**（`g_pos_retry_max_err` 默认 2）：随机词 err≤2 概率 ~1.5e-5/组合，36×1140 期望 FP<1，实测全 cache **0 FP**。auto 路径仍用 err≤3（单次比较，0 FP 已验证），仅 pos_retry 收紧。代价：丢失 41 张真实 err=3 救回（err≤3 共 +71，err≤2 +29）。

### 25.6 否决的判伪器：一致性复现（agree≥2）

尝试"err>2 时要求同一码字在 ≥2 组合复现"区分真实/伪纠解--**无效**。实测所有救回（真实 + FP）均 **agree=1**：每个偏移产生不同码字，真实 1 比特移位仅由唯一精确偏移救回，无相邻复现。FP（err=3, agree=1, dot_num=152）与真实 err=3 案例在 err/agree/dot_num 上**均不可区分**。一致性代码已移除（死代码）。

> 方向一（pos_retry err=3 安全救回）已否决：err=3 的 41 真实救回 vs 1 FP（cache5 68719476735）在 err/agree/dot_num/置信度（avg/min/max）上**均不可区分**。置信度门控实测：FP avg=23/min=0/max=53 vs 真实 avg=23-26/min=0-5/max=32-52，FP max=53 vs 真实 max=52 仅 1 单位裕度（过拟合 1 个 FP），avg/min 完全重叠，不可分离。per-curve 一致性不适用（c2/c3 24/23-bit 块非独立 BCH 可解）。安全救回 +42 需全新信号，暂搁置。

### 25.7 经验总结

1. **极性 ≠ 位置**：`force_peak` 改极性不改位置。诊断失败必须区分"极性误判"（极性重试可救）与"位置错位"（需位置重试）。cache2 +0 的真因是位置错位被误判为"真退化"。
2. **边界偏移 vs 相位偏移**：移动 sync_pos 边界破坏子段划分（+0）；平移比特中心相位（不动边界）才是正确机制。
3. **多重比较需收紧阈值**：N 组合重试使伪可解概率放大 N 倍。pos_retry 36 组合用 err≤2（比基线 err≤3 严）维持 0 FP。
4. **一致性判伪器需验证再采用**：直觉上"真实移位应在相邻偏移复现"听起来合理，但实测 agree 恒为 1--离散整数偏移每步产生不同码字。采用前必须实测分布。

## 二十六、第十四阶段调研：多帧信号平均（否决 - 失败为位置错位非噪声）

### 26.1 假设

连续视频帧对同一盾牌，逐像素/逐曲线平均可提升 SNR，救回 BCH 失败帧（fail_stage=5）。

### 26.2 图像平均实验（test_multiframe，6 帧 cache2 BCH 失败帧）

| 方式 | 结果 |
|------|------|
| 单帧（6 帧） | decode=0, fs=5, dn=149（全部 BCH 失败） |
| 6 帧逐像素平均 | decode=0, **fs=1, dn=0**（平均模糊致定位失败） |
| 留一法 5 帧平均 | decode=0, fs=5, **dn=264**（平均产生伪轮廓点，tracer 误检） |

**图像平均不可行**：帧间盾牌亚像素位移，平均模糊 Pattern 比特细节，定位失败或产生伪点。

### 26.3 根因：失败是**位置错位**非**噪声**（决定性证据）

逐比特比对 cache2 MISS00000/00001/00002（连续同盾帧）：

```
c0(0-7)   got: 10110011  exp: 10110011  (0 errs)   ← 完美
c1(8-15)  got: 11111010  exp: 11111010  (0 errs)   ← 完美
c2(16-39) got: 000101101001101000000000  exp: 000010110100110100000000  (10 errs)
c3(40-62) got: 10010011101110101011000  exp: 10010111011010100110000  (7 errs)
```

关键发现：
1. **三帧比特完全相同**（c0/c1/c2/c3 逐位一致）→ 无随机噪声可平均消除。
2. **c2 = exp 整体左移 1 比特**（got[i]=exp[i+1]，i=0..22 精确匹配）→ 系统性位置错位，非散落噪声。
3. c0/c1（短弧）0 误差 → 信号本身干净，仅长弧采样对齐错。

**多帧平均减噪声不减位置错位**。连续帧产生相同比特，平均后仍是相同比特（波形更平滑但比特判决不变）。

### 26.4 附带发现：pos_retry 无法修复整块 1 比特移位

c2 整块左移 1 比特，理论上 (sync1_off=1, sync2_off=1) 应使三子段相位 ph1=ph2=ph3=1 统一右移 1 比特。实测 `{1,1}` 仅得 8 errs（非 0），且 pos_retry 全部 36 组合均未救回。

**原因**：wave2bits63_2 的子段边界 sync_pos1/sync_pos2 由波同步检测，整块移位时边界与比特同步移动；per-sub-segment 相位偏移（相对边界）无法抵消整块移位。修复需更深机制（如平移曲线采样起点），留作后续优化点。

### 26.5 经验总结

1. **平均类方法仅对噪声受限失败有效**：验证前必须诊断失败是噪声型（散落随机错）还是位置型（系统性移位）。本案例 c0/c1 完美 + c2 整块移位 = 位置型，平均无效。
2. **连续帧相同比特即否决信号**：若多帧比特一致，说明无噪声可平均，平均类方法必无效。
3. **整块移位 vs 子段相位**：per-sub-segment 相位偏移能修子段内偏移，不能修跨子段边界的整块移位。

### 26.6 全部优化累计（无变化）

本调研为否决项，无代码变更。**最终发布得分不变**：2519 图，1407 解码（55.9%），0 FP 0 回归。

## 二十七、第十五阶段：wave2bits 长弧 setup 缓存（wave 2.4×，总 -31%，bit-exact 0 FP 0 回归）

### 27.1 背景：方向三（NEON SIMD）验证 - NEON 是错误工具

阶段计时剖析（test_profile，2 loop）揭示 wave 阶段占 58%（~1435us/img），看似 NEON 加速目标。但关闭重试后 wave 仅 22us/img（2.2%）：

| 配置 | wave us/img | wave % | total ms/img | HIT |
|------|------------|--------|-------------|-----|
| 无重试（mode=0） | 22 | 2.2% | 1.23 | 226 |
| shipped（mode=1） | 1435 | 58.1% | 2.84 | 352 |

**wave 热点全部是重试冗余**：失败帧跑满 57 次重试（auto 1 + c3_retry 4 + c2_retry 16 + pos_retry 36），每次重跑整个 wave2bits63_2（trim/match_sync_pos/th/二值化/采样）。NEON 加速 22us 的单次内循环 -> 总收益 <2%，且 NEON 为 ARM 专属无法本地（MSVC x86）A/B 验证。**NEON SIMD 否决**。

### 27.2 根因：重试只改 setup 的 1 个参数，却重算全部

wave2bits63_2 的计算分两部分：
- **setup**（trim_head_tail + match_sync_pos×2 + rectify + 4 阈值 + 3 子段二值化/s-e 检测）：依赖 (wave, len, force_peak, min_span)，与 sync_off/phase **无关**。
- **sample**（3 段比特中心亚像素采样循环，~30 次运算）：受 phase_off 影响。

重试只改 force_peak（极性重试）或 sync_off（位置重试）。pos_retry 36 组合全用 force_peak=-1（auto），setup 完全相同却重算 36 次。c2/c3_retry 共 5 种极性组合（auto + 4 PEAK_COMBOS），却重算 57 次。

### 27.3 方案：setup/sample 拆分 + 按 (force_peak, min_span) 缓存

1. **拆分 wave2bits** 为 `wave2bits_setup`（二值化+同步游程 s/e 检测+跨度检查，可缓存）+ `wave2bits_sample`（比特采样循环，受 phase 影响）。原 wave2bits 改为调用二者（bit-exact，代码逐行取自原函数）。
2. **wave2bits63_2 缓存**：setup 结果按 (force_peak1, force_peak2, min_span) 存入 10 槽缓存（2 长弧 × 5 极性组合）。命中则跳过 setup，仅重跑 3 段 sample。诊断模式（g_dump_wave）走原始未缓存路径，保留 dump 输出。
3. **缓存生命周期**：try_full_decode 入口 reset（曲线已采样、重试开始前）；decode_pipeline_model 重采样曲线后 reset（防跨帧同缓冲区陈旧命中）；min_span 变化（span_retry）自然 miss 重算。

setup 调用次数：57/curve -> 5/curve（c2、c3 各 5 种极性），10 次替代 114 次。

### 27.5 经验总结

1. **先剖析再优化**：NEON 假设 wave 内循环是热点，实测重试冗余才是（65× 单次）。单次仅 22us 的循环 SIMD 化收益 <2%。性能优化必须先量化各阶段与单次/重试占比。
2. **缓存优于向量化去冗余**：重复计算相同结果时，缓存（不重算）比向量化（更快重算）高一个数量级。先识别计算不变量。
3. **setup/sample 拆分保 bit-exact**：把函数拆为"与重试参数无关的 setup"+"受重试参数影响的 sample"，setup 缓存、sample 重算。拆分逐行取自原函数，wave2bits 仍调 setup+sample，零行为差异。
4. **缓存键须含所有影响因素**：force_peak（极性重试改）、min_span（span_retry 改）入键；曲线重采样（同缓冲区复用）须显式 reset，不能靠指针判同。

## 二十八、第十六阶段：pos_retry 单弧偏移扩展（+157 解码，0 FP 0 回归，历史最大单次绝对增益）

### 28.1 背景：pos_retry 36 联合组合的覆盖盲区

pos_retry（第二十五阶段）对 c2/c3 长弧同步位施 ±1 比特相位偏移联合重试，每弧 6 种非零偏移 `SYNC_OFFS[6]={{1,0},{-1,0},{0,1},{0,-1},{1,1},{-1,-1}}`，c2×c3 联合 36 组合，err≤2 接受。救回 +29 解码。

**盲区**：36 组合要求 c2、c3 **均为非零偏移**（`a∈0..5, b∈0..5`，下标对应非零条目）。它**从不尝试"仅一弧偏移"**（c2=0,0 配 c3≠0,0，或 c3=0,0 配 c2≠0,0）。auto 路径是唯一的 (0,0,0,0)。

### 28.2 诊断：mode-0-direct phase sweep 揭示单弧漏救（推翻 26.4）

构建 `test_phasesweep`：禁用全部重试（c3/c2/pos/span/chase=0），手动设 c2/c3 同步相位偏移，单次 63-bit 解码读 bits63_raw，逐子段比对 ground truth。模式 mode-0-direct（trace_fb=0, try_both=0, model=0）取最干净的单曲线，规避 shipped 管线早退导致的曲线歧义。

**cache2 全 519 图 mode-0-direct sweep**：229 图可解（某相位下 err≤3），其中 **75 图"会解但 shipped 未解"= 漏救**。逐帧分析 75 图的联合相位（best c2 + best c3）：

| 联合 total err | 帧数 | 说明 |
|----------------|------|------|
| 1 (bch=1) | 69 | err≤2，单弧即可救 |

## 二十九、第十七阶段：retry 级优化触顶确认与 c3 硬失败根因剖析（结论：62.0% 为 retry 天花板）

### 29.1 背景：单弧扩展后剩余失败的桶分布

单弧扩展（第二十八阶段）将解码率推至 62.0%（1564/2519）后，对全部 956 张失败图按 fail_stage 重新分桶（test_faildist，shipped 配置，ret=0 真失败）：

| 失败桶 | 数量 | 占比 | 性质 |
|--------|------|------|------|
| BCH err=-1 (>5 不可纠) | 328 | 52% | c3-dominant(~280) + spread(~48) |
| locate 失败 (stage1) | 99 | 16% | 多为 cache6 出画面/小盾，图像质量 |
| trace 失败 (stage2) | 68 | 11% | centroid+model 双失败，多为硬帧 |
| BCH err=5 | 34 | 5% | t=5 伪纠 FP 风险，已拒(err≤3) |
| 其余 (curve/wave/err1-4) | 余 | — | err1-4 = 0（无近临可救） |

**BCH err=-1 (328) 是绝对主导失败桶**，其中 ~280 帧为 c3-dominant（c0+c1+c2≤3 且 c3≥5，典型 c3=9）。err=1..4 = 0 说明不存在"差 1~4 比特即可救"的近临帧——retry 已榨干近临空间。

### 29.2 假设一：相位扩展 ±2/±3（推翻）

pos_retry 现有 SYNC_OFFS 仅 ±1。假设 c3 残差可用更大相位偏移修复。test_phaseext 在 mode-0-direct 下扫 ±1/±2/±3 单弧一致+单 sync 偏移：

- **结果：仅 +3 救回（cache2）**。195 cache2 "none" 帧在所有相位（至 ±3）下仍 >5 错——非相位可修。
- 结论：相位扩展 ROI 过低，放弃。

### 29.3 假设二：c3 同步边界整体平移（推翻）

c3 残差早期观察似集中在子段边界（display 0 / 7-11 / 22）。假设是 sync_pos1/sync_pos2 错位，phase_off 只移子段内比特中心不动边界，故边界比特不可修。新增诊断 `g_c3_sp1_shift/g_c3_sp2_shift`（match_sync_pos 之后平移 c3 两边界 ×sample_per_bit），test_c3spshift 在 cache3 202 c3-dominant 帧扫 {-2,-1,-0.5,0,0.5,1,2}：

- **结果：sp_shift 单独救回 0，sp_shift+phase(-1,-1) 救回 0**。最佳平移(-2,-2)仅使 c3 err 9->8（+phase 到 7），远未到 ≤3。
- 结论：移动边界不能修 c3 错误。match_sync_pos 已搜 ±2，在其上再平移无效。诊断已回退（Wave2Bits.cpp/h 恢复 HEAD）。

### 29.4 c3 错误的真实形态：中段离散、确定性（非边界、非噪声）

对纯 c3-dominant 帧 HIT00035（shipped 下 0/0/0/9）dump 波形/阈值/比特（test_dump，auto 尝试）：c3 错误位于 **子段中段**（binary 4,6,7 / 12,14,15 / 18），**非子段边界**。结合多帧调查（[[isliicon-multiframe-averaging-rejected]]：连续帧比特完全相同），c3 错误是**确定性的**——同一物理位置在多帧间一致出错，既非随机噪声（不可平均）亦非边界错位（不可平移）。

根因：edge[3] 波形在特定物理位置（盾牌角落附近/弧中段）因透视/曲率/模糊而退化，线性逐子段位周期模型（常 det）与线性阈值坡（th0-th1-th2-th3）无法在该处正确提取。这是**采样/波形质量问题，非 retry 可修**。

### 29.5 结论：retry 级优化在 62.0% 触顶

三个 retry 级假设（相位扩展 / 边界平移 / 单弧已发布）穷尽后，剩余 328 BCH 硬失败需**算法级改动**方能动：
- 更鲁棒的 sync 检测（match_sync_pos 锁错时多假设）
- 透视感知/非线性位周期采样
- 逐比特自适应阈值

此类改动高风险（FP / 破坏 Android bit-exact）、高投入，且可能如边界平移般无收益。经评估，**接受 62.0%（1564/2519，0 FP）为 retry 级解码率天花板**，解码率算法优化告一段落，转向其他方向。

- 已刻画：328 BCH 硬失败 = c3-dominant(280, 确定性中段离散) + spread(48) + err=5(34, FP 风险)。

## 三十、第十八阶段：corner_score_S 高斯核循环裁剪（corner 提速 2.4-2.6x，bit-exact 0 FP 0 回归）

> 解码率优化于 62.0% 触顶后（第二十九阶段），转向**性能**维度。corner 阶段是最大固定成本阶段（cache1 占 35.7%，cache6 占 23.7%），其中 `corner_score_S`（Harris 式结构张量）为内层热点。本阶段为性能优化的第一个点。

### 30.1 瓶颈定位

corner 阶段 = `do_corner_finder`（角度法角点检测）+ `finetune_corners`（4× `fine_tune_corner_coord` 图像搜索）。`fine_tune_corner_coord` 对每个候选像素调用 `corner_score_S` 计算结构张量响应 `|sumIx2·sumIy2 − sumIxy²|`，高斯窗口半径 `r2 = 0.5·frame_width`（实测 ~20-26）。

`corner_score_S` 的核循环为 `(2r2+1)²` 次迭代，r2≈26 时约 2601 次。逐次 A/B profile 显示 `corner_score_S` 是 corner 阶段的主热点。

### 30.2 关键发现：高斯核有效支持半径 ≈ 2，98% 迭代为恒零

高斯核 `m = exp(−(u²+v²))`（**无 sigma**，CornerFinetuner.cpp `create_guass_kernel`），衰减极快。`precompute_smooth` 输出 S 为 8 位（0-255），故梯度 `Ix = S[a]−S[b] ∈ [−255, 255]`。逐元素取整 `Ix = (int)(Ix·m + 0.5)`，**round(Ix·m) ≠ 0 要求 |Ix|·m ≥ 0.5**：

- 最坏情况 |Ix|=255：需 `255·exp(−(u²+v²)) ≥ 0.5`，即 `u²+v² ≤ ln(510) ≈ 6.23`。
- 即所有非零贡献点都在**切比雪夫半径 2** 内（2²+2²=8 > 6.23，故半径 2 已含边界；半径 4 时 4²+4²=32，255·exp(−32)≈3.5e-12，远低于 0.5）。

结论：r2≈26 时，2601 次核迭代中仅 ~21 次（半径 2 内）非零，**98% 为恒零项**（Ix=Iy=0 → 对 sumIx2/sumIy2/sumIxy 贡献 0）。这些迭代被无条件计算但永不改变结果。

### 30.3 优化：核循环裁剪至有效半径（bit-exact by construction）

```c
static const int CORNER_KERN_EFF = 4;  // 高斯有效支持半径上界（8x 安全余量）

// corner_score_S: 核循环用 r_kern，边界检查仍用 r_bounds(=r2)
for (int v = -r_kern; v <= r_kern; v++)
  for (int u = -r_kern; u <= r_kern; u++) { ... }

// fine_tune_corner_coord:
int r_kern = (r2 > CORNER_KERN_EFF) ? CORNER_KERN_EFF : r2;
double* guass_kernel = create_guass_kernel(r_kern);  // 小核
// 边界检查传原 r2：score = corner_score_S(..., r_kern, r2);
```

**bit-exact 保证（构造性，非经验）：**
1. 跳过的项满足 `u²+v² ≥ 25`（r_kern=4 之外），`255·exp(−25) ≈ 3.5e-9 < 0.5`，故 `round(Ix·m)=0`、`round(Iy·m)=0` → 对三个累加和贡献恰好 0。累加和不变 → 返回值逐位一致。
2. 边界检查仍用原 `r2`（`r_bounds`），保持"哪些候选因越界返回 0"的语义不变。
3. `create_guass_kernel(r_kern)` 构建更小核数组，但 `corner_score_S` 以相同 u,v 顺序 `*gk++` 索引，|u|,|v|≤r_kern 的权重与原核一致（exp 确定性）。

故每次 `corner_score_S` 返回值与基线完全相同 → `find_2peaks` 相同 → 角点坐标相同 → 整条流水线输出逐位一致。

## 三十一、第十九阶段：calc_center_shift SIMD 加速（trace 提速 ~25%，bit-exact 0 FP 0 回归）

### 31.1 背景与动机
corner 核裁剪（第三十节）后 corner 阶段从 ~35% 降至 ~14%，trace 阶段（~22-29%）成为新的最大阶段。trace 内 `calc_center_shift` 是热点：对 CircleArea（半径 ≈1.1×frame_width ≈57，subsample=2）逐行计算暗像素质心，内循环为

```
for(xx=xstart; xx<xend; xx+=2) if(ppixel[xx]<=th){cx+=xx-ox; cy+=y; cnt++;}
```

每像素一次比较 + 条件累加，分支密集，是 SIMD 的典型目标。

### 31.2 方案
新增 `ccs_row_simd` 内联助手，subsample=2 时替代标量内循环：

- **x86_64**：SSE2/SSSE3（`_mm_shuffle_epi8` 取偶字节；偏置 0x80 转有符号比较实现无符号 `≤th`；`unpack`+`srai` 符号扩展；`_mm_madd_epi16` 掩码点积）。
- **arm64-v8a**：NEON A64（`vqtbl1q` 取偶字节；`vcleq` 无符号比较；`vmovl`+`vshr` 得 dark01；`vmulq` 掩码乘；`vpaddlq`+`vaddvq` 水平求和）。
- **armeabi-v7a（arm32）**：标量回退。A64 专用内建（`vaddvq`/`vqtbl1q`）在 arm32 不可用，NEON 路径以 `#if defined(__aarch64__)` 守卫，arm32 不含 SIMD 代码、走原标量循环。

bit-exact 由构造保证：每 16 字节取偶字节 = subsample=2 的同样像素集；掩码点积 = 相同整数累加；标量尾部（<16 字节）与原循环逐位相同。

### 31.3 运行时开关
`g_ccs_simd_enable`（默认开）+ `islii_set/get_ccs_simd_enable`，用于同会话受控 A/B，消除系统负载噪声对测量的干扰。

### 31.4 bit-exact 证明
1. **像素集**：`even_tbl={0,2,4,6,8,10,12,14}` 取出的字节 = 标量 `xx+=2` 访问的像素，一一对应（含未对齐 xstart，因 vld1q/_mm_loadu 支持非对齐加载）。
2. **判定**：`vcleq`（NEON）/ 偏置 0x80 + `cmpgt` + xor（SSE2）实现无符号 `≤th`，与标量 `ppixel[xx]<=th` 等价。
3. **累加**：dark01(0/1) × idx 掩码点积求和 = Σ(xx-ox) over dark；cnt = Σdark01；cy = y×cnt，与标量逐项相同。
4. **尾部**：不足 16 字节部分走原标量循环。

### 31.5 A/B 验证
- **x86_64 SSE2（端到端解码器，2519 图）**：受控开关 A/B，1564 解码完全一致，0 回归 0 FP。
- **arm64-v8a NEON（qemu-aarch64 独立 fuzz）**：2,005,159 组（2,000,000 随机 + 边界用例（全黑/全白/斜坡/空区间/每对齐 0..15 × 小跨度 1..20 × 多阈值/阈值边界），NEON 与标量参考逐位一致 → PASS。

## 三十二、第二十阶段：corner 高斯核半径收紧 4→2（corner 提速 ~30%，bit-exact 0 FP 0 回归）

### 32.1 背景与动机
SIMD trace（第三十一节）之后，依次验证下一性能点。先做 corner 内部剖析：在 `fine_tune_corner_coord` 四个子步骤（clip / precompute_smooth / score 循环 / find_2peaks）加临时子计时，结果出乎此前预估——**score 循环占 corner 的 58-59%**（`corner_score_S` 逐边界点计算），而 `precompute_smooth` 仅占 14-17%：

| cache | clip | smooth | score | find2peaks |
|-------|------|--------|-------|-----------|
| cache1 | 8.3% | 17.2% | **58.6%** | 6.5% |
| cache6 | 6.1% | 13.9% | **58.8%** | 5.0% |

`corner_score_S` 的核循环半径由 `r_kern = min(r2, CORNER_KERN_EFF)` 决定。第三十节已将 `CORNER_KERN_EFF` 从 r2 收紧到 4（9×9=81 次迭代），注释明确指出**非零贡献的真正边界是切比雪夫半径 2**，4 是“8x 安全余量”的保守值。故 4→2 是对既有 bit-exact 裁剪优化的严格收紧。

> 测量学旁注：本阶段同时发现 `test_profile` 在计时循环内每图调用 `isli_icon_decoder_init/uninit`，而 JNI 层 `nativeInit/nativeUninit` 在生产中各只调一次（`nativeDecode` 才按帧调）。故 init/uninit 的 ~165μs/图（重建 BCH 表 + 内存池，与图像无关的常数开销）是**测试台架伪开销**，不在生产单帧成本中。它不干扰 A/B（固定加性开销抵消），但会压低各阶段百分比、并主导“OTHER”桶。后续剖析应扣除该项。

### 32.2 方案
`CORNER_KERN_EFF` 4→2。核循环从 9×9=81 次迭代降到 5×5=25 次（3.24×）。边界检查仍用原 `r2`（保持哪些候选返回 0 不变），仅核循环半径收紧。

### 32.3 bit-exact 证明（by construction）
高斯核 `m = exp(-(u²+v²))`，`S` 为 8 位故 `|Ix| ≤ 255`。`round(Ix·m) = (int)(Ix·m + 0.5) ≠ 0` 要求 `|Ix|·m ≥ 0.5`。最坏 `|Ix|=255` 时 `m ≥ 0.5/255 ≈ 0.00196`，即 `u²+v² ≤ ln(510) ≈ 6.23`。
- 切比雪夫半径 2（5×5）覆盖全部非零点：`(2,1)/(1,2)` 的 `u²+v²=5 < 6.23` 非零；`(2,2)` 的 `u²+v²=8 > 6.23`，`m=exp(-8)=3.35e-4`，`255·3.35e-4=0.085 < 0.5` → 贡献为 0。
- 半径 ≥3 的点 `m ≤ exp(-9)=1.23e-4`，`255·1.23e-4=0.031 < 0.5` → `(int)(Ix·m+0.5)=0` 恒成立，对 `sumIx2/sumIy2/sumIxy` 无贡献。

故 `r_kern=2` 与 `r2` 完整核产生逐位相同的 `Ix/Iy` → 相同 score → bit-exact。证明仅依赖 `|Ix|≤255` 与核指数衰减，与图像内容无关，无需经验取证。

### 32.4 A/B 验证
- 解码数：`r_kern=4` 基线 1530（cache1-6 try-both correct 全量）= `r_kern=2` 1530，逐 cache 逐位一致（cache1 257/257、cache2 257/257、cache3 144、cache4 333、cache5 110、cache6 429）。
- cache7（352 图，独立集）：`r_kern=4` 与 `r_kern=2` 均 118 解码 / 54 correct / 53 匹配 03000000461，逐位一致。
- FP：try-both(err≤3) 各 cache 解码数=correct 数，0 FP。

| cache | 阶段 | r_kern=4 | r_kern=2 | 增益 |
|-------|------|----------|----------|------|
| cache1 | corner | 177.26 μs | 125.35 μs | **−29.3%** |
| cache1 | total wall | 1.210 ms | 1.154 ms | **−4.6%** |
| cache6 | corner | 91.24 μs | 63.72 μs | **−30.2%** |
| cache6 | total wall | 0.853 ms | 0.808 ms | **−5.3%** |

trace/curve/wave/bch 持平，证实改动严格隔离在 `corner_score_S` 核循环。

### 32.6 ABI 兼容
仅常量值变更 + 注释，无新代码/内建。NDK aarch64 + armv7a `-fsyntax-only`（`--sysroot`）均 rc=0；MSVC 端到端运行验证。三 ABI 一致。

## 三十三、第二十一阶段：wave 滑动窗口整数求和优化（**经测量否决**，0 代码改动）

### 33.1 假设与动机
继 corner 核循环裁剪（第三十二节）后，下一个候选热点为 wave 阶段（cache1 占 stages_sum 38%，avg 322μs/图，当前最大阶段）。`Wave2Bits.cpp` 中 `match_sync_pos` / `match_sync_010` 各有一个滑动窗口整数求和：

```c
for (int i = s0; i < s1; i++){
    int sum = 0;
    for (int j = 0; j < sample_per_bit; j++) sum += wave[i + j];   // sample_per_bit ≈ 94
    score[i - s0] = sum;
}
```

每窗口 O(spb) 加法，可改为滑动求和（O(1)/窗口，`sum += wave[i+spb-1]; sum -= wave[i-1];`），理论减少 ~47× 加法。**整数算术可结合，bit-exact。**

### 33.2 剖析方法（先剖析再优化）
在 `Wave2Bits.cpp` 临时插桩（WSUB 计时器）分别计量三处：滑动求和循环（match_sync_pos + match_sync_010）、二值化循环。`test_profile` 累加打印 wave 子阶段占比。5-loop MSVC Release。

### 33.3 测量结果（决定性）

| 缓存 | wave 总 (μs/图) | 滑动求和 (μs/图) | 占 wave | 二值化 (μs/图) | 占 wave |
|---|---|---|---|---|---|
| cache1 | 322.38 | **0.31** | **0.1%** | 1.21 | 0.4% |
| cache6 | 187.49 | **0.08** | **0.0%** | 0.69 | 0.4% |

滑动求和仅占 wave 的 **0.0~0.1%**。即便 47× 加速，每图只省 ~0.3μs（总 <0.1%）。

### 33.4 根因：长弧 setup 缓存（已发布）已令该循环几近免费
wave 主热点在历史剖析中已确认为**重试冗余**（单遍 wave=22μs，shipped 含 ~15-57 次重试）。长弧 setup 缓存（第十三节，已发布）按 `(cache_id, force_peak1/2, min_span)` 复用 `match_sync_pos`/`match_sync_010`/二值化的 setup——**这些 setup 每组合只跑 1~2 次（首调），后续重试全命中缓存只重算 sample**。故滑动求和已被 setup 缓存"顺便"消除，无需再手动滑动化。残余 wave 成本（322μs）属重试编排 + 每重试 sample 路径 + 失败帧的 112-bit wave（未插桩），均为改变解码输出即不安全的控制流，非可安全压缩的紧循环。

### 33.5 结论
**否决，0 代码改动。** 与第十九阶段 precompute_smooth 滑动求和否决同型（先剖析→实测过小→放弃）。临时插桩已全部清理（Wave2Bits.cpp/.h、test_profile.cpp 回到 HEAD，无残留）。**印证方法论**：wave 段经 setup 缓存后已无可安全压缩的紧循环热点，安全性能杠杆在该段已耗尽。

## 三十四、性能优化维度收尾：四阶段穷尽性核查（结论：当前架构下安全杠杆已耗尽）

### 34.1 背景
"依次验证"序列已完成：① corner 核半径 4→2（第三十二节，已发布）；② wave 滑动求和（第三十三节，经测量否决）。本节对其余两大阶段（trace、curve）及 corner 残余做穷尽性结构核查，判定是否还有 bit-exact 安全杠杆。

### 34.2 各阶段现状（cache1 profile，post-corner-cut）

| 阶段 | μs/图 | 占 stages_sum | 现状 |
|---|---|---|---|
| trace | 201 | 23.7% | ccs SIMD 已发布（trace −24.7%）；见 34.3 |
| corner | 125 | 14.7% | 核循环 4→2 已发布；残余 clip/smooth/find2peaks 见 34.4 |
| curve | 179 | 21.1% | **锁定**：27 抽头 double 低通（NEON float 曾致 FP） |
| wave | 322 | 38.0% | **锁定**：经测量，整数循环已被 setup 缓存消除，残余为重试编排（第三十三节） |
| bch | 21 | 2.5% | 小，BCH 表查表 |

### 34.3 trace 结构核查（结论：无安全杠杆）
`calc_center_shift`（每点质心，trace 内循环核心）含两循环：
- **阈值估计循环**（采样中心行 `xx+=3` + 中心列 `yy+=3`）：≈ 2×(2r/3) 次读，r≈30 时 ≈40 次。
- **质心累加循环**（2r+1 行 × len，subsample=2）：≈1830 次读，**已 SIMD**（`ccs_row_simd`）。
  阈值循环仅占 ccs 读取量 ~2%，可忽略；质心循环已优化。
- `init_CircleArea` 每 `trace_once` 调用 2 次 heap alloc（new[]/delete[]），≈8 次/解码 × ~100ns ≈ 1.6μs = **stages_sum 的 0.2%**，可忽略。
- 每步 `sqrt` 归一化、`amend_center` 的 `MAX_TRY=3` 迭代：均为改变即影响追踪轨迹→改变解码输出，**锁定**。
  结论：trace 热点已被 ccs SIMD 捕获，无可安全压缩的残余紧循环。

### 34.4 corner 残余核查
核循环（score-loop，原 59%）经 4→2 已压缩。残余 ~40% = clip（2 遍，结构性必需）、precompute_smooth（3×3 整数均值，经测量仅 31μs/图，第十九阶段已否决滑动求和）、find_2peaks（小）。均无 bit-exact 安全压缩空间。

### 34.5 整体结论
**当前解码器架构下，bit-exact 安全性能杠杆已穷尽。** 两个真实杠杆（corner 高斯核裁剪、ccs SIMD）均已于本维度前期捕获并发布；此后三个候选（precompute_smooth 滑动求和、wave 滑动求和、trace 结构核查）均经测量/结构分析否决。所有残余大成本要么**锁定**（curve double 滤波、wave 重试编排、trace sqrt/MAX_TRY、locate 线性扫描——改变即非 bit-exact 或改变解码输出），要么**已被缓存消除**（wave setup），要么**可忽略**（<2%）。

进一步性能提升需跨越 bit-exact 约束（接受浮点近似/算法重写，带 FP 风险）或架构级重构（如重试调度合并、locate 早退），属高风险高工作量，**当前不予推进**。

## 三十五、收尾：Release 构建关闭日志输出（编译期 no-op，0 FP 0 回归）

### 35.1 背景
icon/line 两解码器日志原为**运行期级别门控**（cheap 整型比较），且头文件注释明确"始终编译（Release 也生效）"以保证真机可采日志。默认级别 INFO，而 JNI bridge 不调用 `set_log_level`，故生产 Release 实际按 INFO 往 logcat 输出阶段级日志。用户要求 Release 不输出日志。

### 35.2 方案：NDEBUG 编译期门控
以标准 Release 标记 `NDEBUG` 门控日志宏（CMake Release / MSVC Release 均定义；Debug APK 不定义 → 仍可采日志，作排查安全阀）：

```c
#if defined(NDEBUG)
#define ISLII_LOGE(...) do {} while (0)   // 四级全 no-op，参数不求值
... 
#else
  // 原运行期级别门控（Android logcat / PC stderr）
#endif
```

- **icon**（`isli/IldLog.h`）：顺带去重平台间重复的级别常量 + level API（原 Android/PC 两份各 14 行），重构为"平台后端 / 级别常量 / API / 宏(NDEBUG?Android?PC)"四段，可读性更佳。
- **line**（`linecode/IldLog.h`）：最小改动，仅给 `ILD_LOG*` 四宏加 `NDEBUG` no-op 分支。`ILD_TIMING`（无调用点）与 level API 保留编译以维兼容，Release 下 `ild_log` 因无引用被编译器消除。

### 35.3 bit-exact 安全性
审计全部 103(icon)+45(line) 个日志调用点：**参数均为纯读取**（变量/字段/数组读、简单算术），无 `++`/赋值/副作用函数调用。故宏 no-op 不求值参数 → 不改变任何解码状态/输出。

### 35.4 验证
- **bit-exact**：test_diag cache1-6 = 1530 解码、0 FP（N==M），与基线一致。
- **编译**：MSVC Release（NDEBUG）+ NDK aarch64/armv7a × (Debug/Release) 共 4 路径全 PASS。
- **性能**：中性。台架已设 level=ERROR，INFO/WARN/DEBUG 本就跳过；改 no-op 仅省极少数 ERROR 点的级别比较（~ns）。无回归。

### 35.5 阶段产出
- 已发布：`isli/IldLog.h`（重构 + NDEBUG 门控）、`linecode/IldLog.h`（NDEBUG 门控）。
- Release APK 零 logcat 输出（isliicon + isliline 两 tag）；需排查时打 Debug APK。
